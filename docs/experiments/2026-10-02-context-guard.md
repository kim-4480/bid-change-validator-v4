## 왜 했나

2026-10-01 표본으로 처음 채점했을 때 어떤 방식도 핵심 요건의 절반을 찾지 못했다(15개 중 6.7개). 놓친 지역·업종·품명번호·실적 요건 10건을 추적하니 **모델이 못 찾은 것은 한 건도 없었다.** 8건은 안전 가드가 조항에 '또는' 이 있다는 이유로 버렸고, 2건은 조항이 선택되지 않았다.

| 놓친 요건 | 가드가 본 낱말 |
| --- | --- |
| 지역: 경상남도 | "본점 소재지 **또는** 개인사업자의 … 사업장 소재지" |
| 지역: 강원특별자치도 | "사업자등록증 **또는** 관련 법령에 따른 …" (괄호 안) |
| 업종코드 1468 | "소프트웨어 개발·공급 **또는** 컴퓨터 프로그래밍 서비스업" |
| 세부품명번호 4319151001 | "제조 **또는** 납품할 수 있어야" |
| 실적 4억 원 | "농축설비 **또는** 벌꿀 농축공정이 포함된" |

같은 낱말이 문장마다 뜻이 다르다. "입찰참가자격 제한 중이 아닌 자" 는 결격 확인이고, "종합건설사업자의 참여를 제한합니다" 는 배제이고, "실적은 최소요건으로 제한하지 않고" 는 요건이 아니다. 낱말 대조로는 가를 수 없다.

## 바꾼 것

1. **조항의 극성을 모델에게 묻는다** (`bidengine/labeling/clause_polarity.py`). 조항마다 `POSITIVE · EXCLUSION · EXCEPTION · NOT_REQUIREMENT · UNSURE` 중 하나만 고른다. 원문·값·구조는 여전히 코드가 정한다. 같은 조항은 한 번만 묻고, 답은 조항 원문 해시로 기억할 수 있다.
2. **POSITIVE 일 때만 가드를 푼다** (`bidengine/judgment/context_guard.py`). 틀렸을 때의 비용이 한쪽으로 기운다 — 배제를 요구로 확정하면 틀린 판정이고, 요구를 확인 필요로 두면 사람이 한 번 더 볼 뿐이다. 호출 실패나 답 누락은 UNSURE 다.
3. **낱말 규칙은 이견 감지용으로 남긴다.** 모델이 POSITIVE 라 해도 조항에 부정 낱말(참가할 수 없, 제외, 불허 …)이 있으면 확인 필요로 둔다. 낱말 규칙이 혼자 조항을 버리지는 않는다.
4. **닫힌 값은 코드가 센다.** 시·도 이름이 값 구간에 둘 이상이면 대안(ANY_OF), 조항에는 여럿인데 값 구간이 다 담지 않으면 확인 필요. 값 구간 안의 "건축공사업(또는 토목건축공사업)" 은 이름의 대안으로 담는다. 모델이 배제로 읽은 조항에 대기업·중견기업 참여 제한이 적혀 있으면 유형과 무관하게 `COMPANY_SIZE(EXCLUDE)` 로 담는다.
5. 공동수급·대표자 중복·표 참조·절차 문구는 예전 가드 그대로다.

측정하면서 함께 고친 것(가드 설정과 무관하게 적용된다):

- 본문 항목을 자격 절 제목으로 잘못 잡던 것("1. … 입찰참가자격등록규정에 따라 … 완료한 자").
- 줄머리 법령 인용("제12조 및 동법 …")을 조문 제목으로 읽어 자격 절이 끊기던 것. 한 공고는 가~차 항목 중 첫 줄만 선택되고 있었다.
- 문장형 하위 항목("- … 등록한 자")이 한 조항에 일곱 개씩 묶이던 것, "…포함" 에서 문장이 끊기던 것.
- **대기업을 필수 규모로 확정하던 것.** "대기업인 소프트웨어 사업자의 참여가능 사업금액의 하한" 표가 `COMPANY_SIZE 대기업` 필수가 됐다. 중소기업이 미달이 되는, 뜻이 뒤집힌 확정이다. 모델도 이 표를 POSITIVE 로 읽었다 — 극성 판별이 틀릴 수 있다는 실제 사례이고, 배제 조항 정답을 보탠 뒤에야 드러났다.
- "중소기업 또는 소상공인" 이 규모 요건 두 개(둘 다 필수)가 되던 것.

## 남은 것

> 아래 가운데 커버리지 공백 분류, 중복, 자격 절 밖의 조항은 2026-10-03 에 고쳤다 — `2026-10-03-clause-selection.md`.

**아직 못 찾는 핵심 요건 (켠 상태)**

- `C2` 지역 "충청남도 또는 세종특별시", `C3` "종합건설사업자 참여 제한" — 두 조항 모두 자격 절이 아닌 곳에 있어 코드가 고르지 않는다. 모델이 조항을 고르는 실험(`hybrid_selection_probe.py`)에서는 모델이 이 조항들을 골랐다. C3 은 배제 조건이라 선택돼도 지금은 확인 필요로만 남는다.
- `D1` 건축공사업(또는 토목건축공사업) 1/3, `I2` 소기업 1/3 — 모델이 그 조항을 '기타요건' 으로 붙인 실행에서 빠진다. 라벨링 단계의 흔들림이다.

**확인 필요로 남기지 못한 조건** — 공동계약·공동도급 불허 4건(`F4 C4 I3 G8`)은 조항이 선택되지 않았거나 요건으로 올라오지 않아 공백에도 없다.

**오답으로 남은 것** — 업종 요건을 등록·인증 요건으로 한 번 더 뽑는 것(실내건축공사 4990, 제작자등 등록증), "생산시설과 기술인력을 보유" 를 인력 요건으로 뽑는 것.

**중복이 늘었다 (3.7 → 6.3건/회).** 같은 공고문이 HWP·PDF 두 파일로 들어 있으면 같은 요건이 두 벌 나온다. 가드가 풀리면서 두 벌 다 통과한다. 판정 결과는 같지만 차수 비교의 잡음이 된다.

**커버리지 완료율이 0 이 됐다.** 모델이 EXCLUSION·EXCEPTION·NOT_REQUIREMENT 로 읽어 보류한 조항이 전부 '표현 불가' 공백으로 세어지기 때문이다. 부정당업자·조세포탈 같은 공통 배제 조항이 대부분이다. 판정기는 커버리지가 완료일 때만 '적합' 을 주므로, 이대로 켜면 모든 공고가 '자료 부족' 이 된다(끈 상태도 0.083 이라 사정은 비슷하다). NOT_REQUIREMENT 와 공통 배제 조항을 절차 문구로 셀지 정해야 한다.

**재추출 오탐률은 0.44 → 0.41 로 거의 그대로다.** 같은 차수를 다시 추출하면 요건 열 개 중 네 개가 다르게 나온다. 맥락 가드는 정확도를 올렸지 일관성을 올리지는 않았다. 병목은 라벨링 단계다.

## 정답에 대해

`labels.json` 은 원문을 읽고 만든 **초안**이다(상태 `draft`). 기준은 세 가지를 확인받았다 — 공통 항목은 채점에서 제외, 공동수급은 '확인 필요' 로 남겼는지를 봄, 유형이 없는 조건은 가장 가까운 유형으로 적음. 개별 항목은 아직 확인 전이고, 특히 아래는 읽기에 따라 달라질 수 있다.

- `B2`·`H2` "중소기업자 또는 소상공인" 을 '중소기업 이하' 한 건으로 적었다.
- `F3`·`I2` "소상공인, 소기업으로 … 확인서를 소지" 를 '소기업 이하' 로 적었다.
- `G7` "중소기업 확인서 소지(단, 비영리법인 참여 가능)" 를 핵심 요건이 아니라 확인 필요로 적었다.
- 업종 요건과 같은 조건을 등록·인증 요건으로 한 번 더 뽑은 것은 오답으로 셌다.

표본이 9건이고 그 9건을 보면서 코드를 고쳤다. 같은 공고로 고치고 같은 공고로 쟀으므로 0.88 은 새 공고에서 기대할 수치가 아니다. 손대지 않은 공고에 정답을 붙여 다시 재야 한다.
