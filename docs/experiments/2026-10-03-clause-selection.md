# 조항 선택에 모델을 쓸지, 공통 결격·중복 정리 (2026-10-03)

2026-10-02 맥락 가드 실험(`2026-10-02-context-guard.md`)의 후속이다. 그때 남은 세 가지를 고치고, 조항 선택 방식을 재서 정했다.

러너: `eval/experiments/polarity_guard_probe.py --modes clause_polarity hybrid_polarity model_polarity`, 채점: `score_against_labels.py`.
표본·정답은 같다(공고 9건, 핵심 요건 27개, 확인 필요 9개). gpt-6-luna, 20개 차수 × 방식 3 × 3회 = 180회 호출, 오류 0, 24분.

## 결정

**조항 선택은 hybrid(코드가 고른 조항 ∪ 모델이 고른 조항)로 한다.** 세 방식 모두 맥락 가드를 켠 상태다.

| 지표 | code (이전) | **hybrid** | model |
| --- | --- | --- | --- |
| 찾은 핵심 요건 (3회 평균) | 24.3 / 27 | **25.7 / 27** | 24.3 / 27 |
| 재현율 | 0.901 | **0.951** | 0.901 |
| 3회 모두 찾은 요건 | 24 | **25** | 21 |
| 한 번도 못 찾은 요건 | 2 | **1** | 1 |
| 확인 필요로 남긴 조건 (9개 중) | 6 | **9** | **9** |
| 뒤집힌 확정 / 회 | 0 | 0 | 0 |
| 오답 / 회 | 3.0 | **2.7** | 3.0 |
| 중복 / 회 | 1.0 | 0.7 | **0.3** |
| 재추출 오탐률 (20개 차수) | 0.390 | 0.416 | **0.314** |
| 위치 일치도 | 0.849 | 0.823 | **0.884** |
| 값 일치도 | 0.622 | 0.648 | **0.719** |
| 변경 감지 일치도 | 0.173 | 0.152 | **0.409** |
| 라벨링에 넘긴 청크 수 평균 | 18.9 | 21.5 | **9.3** |
| 호출 시간 평균 | 31.8초 | 34.6초 | **27.8초** |
| 커버리지 완료율 | 0.117 | 0.0 | 0.0 |

- **hybrid 는 정확도가 가장 높다.** 자격 절 밖에 있던 지역 요건("충청남도 또는 세종특별시")을 찾고, 공동계약·공동도급 불허 조항 9건을 전부 확인 필요로 남긴다. 코드 선택은 이 조항들을 보지 못한다. 실행마다 빠지는 요건도 가장 적다(27개 중 25개를 3회 모두).
- **model 은 일관성이 가장 높다.** 라벨링 입력이 절반 이하로 줄어 재추출 오탐률이 0.39 → 0.31 이고 빠르다. 대신 재현율은 코드 선택과 같고, 한 실행에서 요건 4개(G2·G5·I1·I2)가 빠졌다 — 모델이 조항을 고르지 않으면 그 요건은 사라진다. hybrid 는 코드가 고른 조항이 밑에 깔려 있어 그런 빠짐이 없다.
- hybrid 의 일관성은 코드 선택과 같은 수준이다(오탐률 0.42 대 0.39, 첫 측정에서는 0.33 대 0.39 — 측정 사이의 흔들림 안이다).

이 제품에서 가장 나쁜 실패는 자격 조건을 놓치는 것이라 정확도가 높은 쪽을 고른다. 일관성을 더 올려야 할 때는 model 이 후보다.

권장 설정(로컬 `.env` 에 적용했다. 저장소 기본값은 그대로다):

```bash
BIDENGINE_EXTRACTION_MODE=clause
BIDENGINE_POLARITY_GUARD=on
BIDENGINE_CLAUSE_SELECTION=hybrid
```

## 2026-10-02 에 남았던 세 가지

코드 선택 기준으로 고치기 전(2026-10-02 최종)과 후를 견준다.

| 지표 | 2026-10-02 | 고친 뒤 (code) |
| --- | --- | --- |
| 재현율 | 0.877 | 0.901 |
| 오답 / 회 | 3.7 | 3.0 |
| 중복 / 회 | 6.3 | **1.0** |
| 확인 필요로 남긴 조건 | 5.0 / 9 | 6.0 / 9 |
| 커버리지 완료율 | 0.0 | 0.117 |

1. **공통 결격 조항을 절차 조항으로 센다.** 부정당업자 제재·조세포탈·휴폐업처럼 모든 입찰자에게 똑같이 걸리는 결격 사유(`COMMON_DISQUALIFICATION`)와, 모델이 자격이 아니라고 읽은 조항(`MODEL_POLARITY_NOT_REQUIREMENT`)은 커버리지 공백이 아니다. 지역·업종코드·품명번호·기업 규모 같은 닫힌 값이 함께 있으면 실제 자격 조건이라 확인 필요로 남긴다. "입찰참가자격 제한" 은 제재를 받는 중이라는 뜻일 때만 결격이다 — "종합건설사업자는 입찰참가자격을 제한합니다" 는 같은 낱말로 쓴 진짜 참여 제한이다.
2. **문서 간 중복을 접는다.** 중복이 늘었던 주된 원인은 맥락 가드가 남긴 기록(`guard_basis`)이 요건의 정체성에 섞인 것이었다. 같은 요건이 한쪽은 code, 한쪽은 model_polarity 로 기록되면 다른 요건이 됐다. 구성원이 전부 같은 대안 묶음(ANY_OF)은 묶음째 한 번만 남기고(일부만 겹치는 묶음은 조건이 바뀌므로 둔다), 세부품명번호가 든 등록 이름은 번호로 통일한다.
3. **자격 절 밖의 조항**은 조항 선택에 모델을 써서 푼다(위 결정).

측정하면서 더 고친 것:

- **공동수급 조항은 코드가 확인 필요로 남긴다.** 1번을 넣자 모델이 "공동수급 및 하도급을 불허" 를 '요건 아님' 으로 읽은 공고에서 그 조항이 절차 조항이 되어 사라졌다. 공동수급·공동계약 낱말은 닫혀 있다. 그런 조항은 극성과 무관하게 예전 가드로 보내고, 모델이 요건으로 올리지 않은 조항도 코드가 찾아 공백으로 남긴다(협정서 제출 같은 절차 문장은 뺀다).
- **"실내건축공사(4990)" 을 업종코드로 읽는다.** 건설 업종은 '업' 없이 적는다. 코드로 읽지 못해 같은 조항이 실행에 따라 업종 요건과 등록 요건을 오갔다. 뒤에 등록·면허가 이어질 때만 읽는다("증축공사(2026)" 같은 연도를 코드로 만들지 않는다).

## 조항 선택이 하는 일 (`bidengine/labeling/clause_selection.py`)

코드가 문서 전체를 조항으로 나누고, 모델은 그 목록을 보고 참가자격 조항의 id 만 고른다. 원문을 쓰거나 경계를 바꿀 수 없고, 없는 id 는 무시된다. 고르는 데는 조항 앞 300자만 보낸다.

- `code` 제목·키워드로 고른 자격 절의 조항 (기본)
- `hybrid` 코드가 고른 조항 ∪ 모델이 고른 조항
- `model` 모델이 고른 조항만. 아무것도 고르지 않거나 호출이 실패하면 코드 선택으로 돌아간다.

분석 한 번에 호출이 문서 크기에 따라 한두 번 더 든다(4만 자마다 한 번).

## 남은 것

- **`C3` "종합건설사업자의 참여를 제한"** 은 여전히 못 찾는 것으로 채점된다. 조항은 선택되고 모델도 배제로 읽지만, 업종의 배제를 담을 구조가 없어 확인 필요로만 남는다. 틀린 확정은 아니다.
- **오답 회당 2.7건.** "제작자등 등록증" 을 업종코드 5898 과 별개의 등록 요건으로 한 번 더 뽑는 것, "생산시설과 기술인력을 보유" 를 인력 요건으로 뽑는 것, "실내건축공사(4990)" 을 면허 요건으로 한 번 더 뽑는 것(3회 중 1회).
- **커버리지 완료율이 0 이다.** hybrid 가 공동수급 조항을 전부 찾아 확인 필요로 남기기 때문이다. 판정기는 커버리지가 완료일 때만 '적합' 을 주므로 공고 대부분이 '자료 부족' 으로 나온다. 공동수급 허용·불허를 '적합' 을 막는 공백으로 둘지, 사용자에게 묻는 질문으로 돌릴지 정해야 한다.
- **재추출 오탐률 0.39~0.42.** 같은 차수를 다시 추출하면 요건 열 개 중 네 개가 다르게 나온다. 라벨링 단계의 흔들림이고, 선택을 model 로 좁히면 0.31 까지 내려간다.
- **표본.** 정답은 초안이고 사람 확인 전이다. 9건을 보면서 코드를 고치고 같은 9건으로 쟀으므로, 0.95 는 새 공고에서 기대할 수치가 아니다. 손대지 않은 공고에 정답을 붙여 다시 재야 한다.
