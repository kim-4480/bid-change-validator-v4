# AI Copilot E1 동일 평가 재측정

기준 브랜치: `feature/ai-copilot-e1-ux-baseline`
E0 기준 commit: `993e5cf446e46c740503ec0840a5996d1f82dfe1`

> 이 문서는 **E0와 동일한 질문/시나리오를 현재 E1 코드 계약에 다시 대조한 재측정**이다. 자유입력 100개는 deterministic routing 재측정이며, I01~I20은 현재 코드 경로와 시나리오 기준의 contract review다. 실제 사용자 E2E, 독립 검토자 승인 정확도, LLM 품질 점수가 아니다.

## 1. 자유입력 100개

| 묶음 | E0 | E1 | 변화 |
|---|---:|---:|---:|
| 문서 QA | 1/60 (1.7%) | 1/60 (1.7%) | +0.0%p |
| 판정 설명 | 0/32 (0.0%) | 32/32 (100.0%) | +100.0%p |
| 변경 비교 | 0/8 (0.0%) | 8/8 (100.0%) | +100.0%p |
| **전체** | **1/100 (1.0%)** | **41/100 (41.0%)** | **+40.0%p** |

해석:
- E1의 상승분은 **고신뢰 자연어 alias와 HELP UX**의 효과다. LLM 의미 이해 성능 향상이 아니다.
- 판정 설명 32개와 변경 비교 8개는 의도한 제품 기능으로 들어가지만, 문서 QA는 **1/60**으로 사실상 그대로다.
- 따라서 E2에서 의미 기반 intent/target 이해, E3에서 실제 근거 기반 문서 QA를 별도로 검증해야 한다.

- 과업 실패: **8/20 = 40.0%** (E0 10/20 = 50.0%)
- 코드 경로에서 확인한 치명적 안전 위반 후보: **0/20 유지**

## 3. E1에서 실제로 해결된 대표 문제

- `I01` 사용법 질문: UNKNOWN 오류 대신 로컬 도움말, API 호출 0회.
- `I02` 자연스러운 참가 질문: `이거 우리도 넣어도 돼?` → 참가자격 요약.
- `I09` 변경 비교 실패: 비교 불가를 `변경 없음`으로 표현하지 않고 원인을 사용자 문장으로 변환.
- `I20` 조회 재시도: 같은 사용자 질문을 새 turn으로 추가하지 않고 기존 실패 turn에서 복구.
- `무엇을 확인해야 해?`: 확인 건수보다 현재 overall status를 먼저 보여 주도록 답변 순서 변경.
- 추천 질문: 일반 화면에서는 변경 비교를 기본 노출하지 않고, 변경 화면에서만 노출.

## 4. E1 이후에도 남은 실패

- 회사 허가 vs 제품 허가처럼 **대상(subject) 구분이 필요한 의미 질문**
- 공고 자체 변경과 회사 영향/재검증을 **서로 독립적인 task로 분리**
- 상충 조항, 계약 수치, 평가항목 vs 필수 자격처럼 **문서 의미를 읽어야 하는 질문**
- 사용자 자연어 진술을 안전한 **답변 초안/업무 상태**로 구조화
- 자격 결과와 제출 마감 같은 **복수 정보 축을 함께 해석**

이 항목들은 alias를 더 늘려 해결하지 않고 E2/E3에서 다룬다.

## 5. 다음 단계 판단

E1은 **고정 규칙으로 확실하게 고칠 수 있는 UX 문제**를 해결하는 단계로 종료한다. 다음 E2에서는 LLM/structured output을 이용하되, 기존 판정·write 안전 경계는 그대로 유지하면서 `intent + target + subject + task state`만 의미 기반으로 해석한다.
