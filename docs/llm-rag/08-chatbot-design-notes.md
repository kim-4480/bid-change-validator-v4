# 08 — 판정 근거 챗봇 설계 노트

> 작성 2026-09-11 · 김재현 (LLM/RAG)
> **이 기능은 다음 커밋에서 제거됩니다.** 팀에서 같은 기능을 따로 구현하고 있어
> 중복을 남기지 않기로 했습니다. 코드는 개인 보관 레포에 남겼고, 이 문서는
> **왜 그렇게 만들었는지**를 남기기 위한 것입니다. 다시 만들 때 같은 함정을
> 다시 밟지 않도록.
>
> 대상 코드: `ai/narration/briefing.py` · `qualification_briefing.py` ·
> `qualification_briefing_router.py` · `ai/demo/web.py` · `ai/demo/web.html`

---

## 1. 무엇을 푸는 기능이었나

판정 화면은 "충족 / 미충족 / 확인 불가"와 근거 원문까지 보여줍니다. 그런데
담당자가 실제로 묻는 것은 그 다음입니다.

```
"왜 미충족이야?"
"그럼 뭘 보완하면 돼?"
"하자보수가 뭔데?"
```

앞의 둘은 **화면에 이미 있는 사실**을 다르게 물은 것이고, 마지막은 **이번 건과
무관한 일반 지식**입니다. 세 종류를 한 입력창에서 받되 **서로 다르게 다뤄야**
한다는 것이 이 기능의 핵심 문제였습니다.

---

## 2. 절대 원칙 — 챗봇은 판정하지 않는다

이 프로젝트의 대원칙은 "판정은 코드, 서술은 모델"입니다(PROJECT.md 3.1).
챗봇은 그 원칙이 가장 깨지기 쉬운 자리입니다. 자연어로 물으면 모델이 답을
지어내고 싶어지기 때문입니다.

그래서 **모델에게 판정 권한을 주지 않는 구조**로 만들었습니다.

```
코드가 판정 → 브리핑으로 확정 → 그 텍스트만 모델에게 → 모델은 설명만
```

모델은 `judge_requirements()`를 부를 수 없고, DB도 보지 못하며, 원문 전체도
받지 못합니다. **이미 끝난 판정을 평문으로 렌더링한 것 하나만** 봅니다.

---

## 3. 핵심 구조 — 사실 출처를 하나로 좁힌다

### 3.1 `render_briefing_text()` 가 유일한 사실 출처

`ai/narration/briefing.py`

이 함수가 이 설계의 중심입니다. 브리핑 객체를 평문으로 렌더링하는데,
**화면에 쓰는 텍스트이자 모델에게 넘기는 유일한 입력**입니다.

```
[공고] 통합정보시스템 구축
  공고번호: R26BK01705963

[참가자격 판정] 적격
  충족 3 / 미충족 0 / 확인 불가 0

  [충족] 최근 3년 이내 실적 5억원 이상을 보유한 업체
      사유: 회사 프로필이 요건을 충족합니다
      근거 기준: 회사 프로필
      공고 원문 (p.2): "최근 3년 이내 실적 5억원 이상…"

[확인 필요 계약조항] 1건
  · 6.1항 지체상금 요율 과다(확인 필요): 공고 값이 표준을 초과
      공고 원문: "지연일수 1일당 계약금액의 0.5%"
      표준: 지연 1일당 계약금액의 100분의 0.125 (시행규칙 제75조제3호)
```

**여기 없는 것은 모델도 모르는 것이어야 한다** — 이 불변식이 환각을 구조로
막습니다. 프롬프트로 "지어내지 마라"라고 쓰는 것보다 **줄 수 있는 정보를
줄이는 쪽**이 훨씬 확실합니다.

함수 독스트링에 이렇게 적어뒀습니다.

> 판정·사유·근거 인용을 전부 담되, **판정을 유도하는 해석은 넣지 않는다.**

### 3.2 그래서 재사용된다

같은 함수가 세 곳에 쓰입니다.

| 소비처 | 용도 |
| --- | --- |
| 화면 | 담당자가 읽는 브리핑 텍스트 |
| `narrate_briefing()` | 구두 설명조로 풀어쓰기 |
| `answer_question()` | 챗봇이 보는 사실 전부 |

**사람이 보는 것과 모델이 보는 것이 같습니다.** 그래서 모델이 없는 말을 하면
담당자가 바로 알아챕니다. 검증 가능성이 구조에서 나옵니다.

## 4. 프롬프트 설계 — 두 종류의 질문을 가르는 법

`CHAT_SYSTEM_PROMPT` (briefing.py)

가장 어려웠던 지점입니다. "지어내지 마라"를 강하게 걸면 **"하자보수가 뭐야?"
같은 정상 질문까지 거부**합니다. 실제로 초기 버전이 그랬습니다.

그래서 규칙을 **사실의 출처별로** 나눴습니다.

```
이번 건의 사실   → [현재 상태] 에 있는 것만. 없으면 모른다고 답하라
일반 지식        → 네가 아는 대로 자유롭게 답해도 된다
판정             → 절대 새로 내리지 마라. 이미 코드가 정했다
```

핵심 문장 세 개입니다.

> 1. 이번 공고에 대한 충족/미충족/확인 불가를 **절대 새로 내리지 마라** —
>    이미 코드가 정했다.
> 2. [현재 상태]에 없는 **이번 건의 구체적 사실**(정확한 금액·날짜·자격 보유
>    여부 등)은 지어내지 마라.
> 4. 반면 **일반적인 지식**은 이번 건 데이터와 무관해도 자유롭게 답해도 된다.

2번과 4번이 짝입니다. **"모르는 것"의 범위를 이번 건으로 한정**해야 도구가
쓸모 있어집니다. 이 구분이 없으면 챗봇이 아니라 거부 기계가 됩니다.

## 5. 대화 맥락 — 이어지는 질문

```python
parts = [f"[현재 상태]\n{render_briefing_text(briefing)}"]
for asked, answered in history or []:
    parts.append(f"[이전 질문]\n{asked}\n\n[이전 답변]\n{answered}")
parts.append(f"[담당자 질문]\n{text}")
```

`history`는 `(질문, 답변)` 쌍입니다. 이게 없으면 **"그럼 그건 왜?"** 같은
대명사 질문에 답할 수 없습니다.

주의할 점이 하나 있습니다. **[현재 상태]가 항상 맨 앞에 오고 매번 새로
렌더링됩니다.** 이전 답변이 사실 출처가 되지 않도록 하기 위해서입니다.
모델이 앞서 잘못 말한 것이 다음 턴의 근거가 되면 오류가 누적됩니다.

데모는 최근 4턴만 넘겼습니다(`HISTORY.slice(-4)`). 길어질수록 비용이 늘고
초반 맥락은 대개 필요 없습니다.

---

## 6. 열화 설계 — 예외를 올리지 않는다

`answer_question()`은 **어떤 경우에도 예외를 던지지 않습니다.** 화면의 부가
기능이 전체를 깨뜨리면 안 되기 때문입니다.

| 상태 | 언제 | 응답 |
| --- | --- | --- |
| `OK` | 정상 | 모델 답변 |
| `EMPTY_QUESTION` | 빈 질문 | "질문을 입력해 주세요" |
| `NARRATOR_UNAVAILABLE` | API 키 없음 | 왜 못 쓰는지 설명 |
| `FAILED` | 모델 호출 실패·빈 응답 | 오류 내용 |

**상태를 문자열로 돌려주는 것이 핵심**입니다. 화면이 "왜 안 되는지"를 사용자에게
말해줄 수 있습니다. 조용히 빈 응답을 주면 고장인지 대답을 못 하는 건지
구분이 안 됩니다.

## 7. 계층 구조

```
ai/narration/briefing.py          answer_question()      순수 함수. DB·네트워크 모름
  └ 입력: question · NoticeBriefing · narrate 콜러블 · history
  └ 출력: ChatAnswer(text, status)

qualification_briefing.py         answer_for_judgment_run()   DB 계층
  └ run_id 로 판정을 읽어 브리핑 조립 → 위 함수 호출

qualification_briefing_router.py  POST .../{run_id}/chat      HTTP 계층
  └ ChatRequest(question, history[]) → ChatAnswer

ai/demo/web.py                    POST /api/assist            데모용
  └ DB 없이 메모리 컨텍스트로 같은 일
```

`answer_question()`이 **콜러블을 주입받는 형태**(`narrate: Narrator | None`)라
테스트에서 모델 없이 프롬프트와 본문을 그대로 검사할 수 있습니다. 이게
다음 절의 테스트를 가능하게 합니다.

## 8. 테스트가 지키던 것

`tests/test_briefing.py` 3건. **동작이 아니라 계약을 지키는 테스트**입니다.

**① 모델이 보는 것이 브리핑뿐인가**

```python
answer = answer_question("실적 요건 어떻게 됐어?", _briefing(), narrate=narrate)
assert captured["system"] == CHAT_SYSTEM_PROMPT
assert "절대 새로 내리지 마라" in captured["system"]
assert "[현재 상태]" in captured["body"]
assert "최근 3년 이내 실적 5억원 이상을 보유한 업체" in captured["body"]
```

가짜 `narrate`로 **모델에게 실제로 넘어간 문자열을 붙잡아** 검사합니다.
프롬프트에서 "절대 새로 내리지 마라"가 사라지면 실패합니다.

**② 이전 턴이 실린다**

```python
assert "[이전 질문]" in captured["body"]
```

**③ 모델이 없거나 실패해도 화면이 안 깨진다**

```python
assert answer_question("  ", ...).status == "EMPTY_QUESTION"
assert answer_question("질문", briefing, narrate=None).status == "NARRATOR_UNAVAILABLE"
assert answer_question("질문", briefing, narrate=broken).status == "FAILED"
```

## 9. 다시 만든다면

**지킬 것**

- 사실 출처를 **하나의 렌더링 함수**로 좁히기. 사람과 모델이 같은 것을 본다
- **판정 권한을 주지 않기.** 모델은 확정된 결과를 읽기만 한다
- 프롬프트에서 **"이번 건 사실"과 "일반 지식"을 명시적으로 가르기**
- 예외 대신 **상태 코드**로 열화하기
- `narrate`를 주입받아 **모델 없이 프롬프트를 테스트**하기

**다르게 할 것**

- **답변에 근거 링크 달기.** 지금은 모델이 인용을 문장에 섞어 쓰는데,
  어느 판정·어느 청크에서 왔는지 구조화해서 돌려주면 화면이 해당 카드로
  스크롤할 수 있습니다
- **history 를 서버가 보관하기.** 지금은 브라우저가 들고 있어서 새로고침하면
  사라지고, 클라이언트가 조작할 수도 있습니다
- **토큰 예산 관리.** 브리핑이 길어지면 매 턴 전체를 보냅니다. 판정 건수가
  많은 공고에서 비용이 선형으로 늘어납니다
