## 2. Q-001 결정 — 정상 경로는 자연스러운 AI 설명, 실패 경로는 근거 있는 부분 반환

**결정: B를 실패 시 기본 반환 정책으로 채택하고, A의 의미 검증·한 번의 수정 시도를 예산 안에서 적용한다.** B는 전체 챗봇을 고정 템플릿으로 되돌리라는 뜻이 아니다.

```text
서버에서 검증한 사실·근거 묶음
→ LLM 통합 답변 초안
→ 기계적 검사 + 필요한 주장들의 일괄 의미 검증
→ 통과한 문장은 자연스럽게 제공
→ 실패/불확실한 문장만 1회 수정 후 재검증
→ 그래도 실패하면 그 문장만 제외·직접 인용으로 대체
→ 확실한 나머지 정보와 구체적인 한계는 계속 제공
```

### 2.1 생성할 수 없는 값과 생성할 수 있는 설명을 분리

- 저장 판정 카드, 입력 가능 건수, 대상/버전 ID, 실행 완료 상태는 서버의 검증된 도구 결과로 생성한다. LLM 출력이 이 필드를 덮어쓰지 못한다.
- 회사 판정 질문이 아닌 순수 공고 QA에 상태 카드를 억지로 반복하지 않는다. 현재 판정이 없거나 오래됐으면 그 상태를 표현하고 문서 QA까지 막지 않는다.
- LLM은 이유·비교·조건 해석·검토 제안을 자연스럽게 작성할 수 있다. 저장 상태와 원문/회사정보의 충돌 후보를 설명하는 것도 허용한다. 엔진을 무조건 정당화하지 않는다.
- 생성된 모든 공고/회사 사실 주장은 conclusion·본문·caveat·next action 어디에 있든 동일하게 검사한다. 본문만 검사하고 결론을 통과시키는 우회 경로를 두지 않는다.
- 직접 인용은 지정 source의 원문과 위치가 맞는지 검사한다. 원문 그대로라는 사실은 법률적 진실·추출 완전성까지 보증하지 않으며 확인한 범위를 표시한다.
- 사용자 발언은 turn ID에 연결된 USER_ASSERTION, 검토용 가정은 ASSUMPTION으로 관리한다. 저장된 회사 사실이나 공고 근거로 승격하지 않는다.
- 인사, 설명의 연결 문장, 사실을 새로 주장하지 않는 일반적 제안은 기계적으로 외부 인용을 강제하지 않는다. 다만 “마감이 내일이니” 같은 사실을 포함하면 그 부분은 검증한다.

### 2.2 W1에 반영할 최소 주장 계약

기본 설계의 EvidenceBundle/AnswerEnvelope에 다음 의미를 수용한다. 필드명은 기존 계약과 일관되게 조정할 수 있으나 역할은 유지한다.

| 항목 | 역할 |
|---|---|
| fact_id | SERVER_RESULT / NOTICE_FACT / PROFILE_FACT / USER_ASSERTION / ASSUMPTION 구분, 값·적용 범위·기준 포함 |
| source_id | 문서/버전/블록/hash/원문 또는 승인된 데이터·대화 출처. 모델이 임의 URL로 생성하지 않음 |
| claim_id | 답변의 개별 주장 식별자. 수정 전후 추적 |
| fact_ids / source_ids | 그 주장을 뒷받침하는 실제 참조. 판정 요건의 존재 여부와 독립 |
| target_id / kind / message_id | 판정 요건·수동 확인·문서 조항·변경 등 대화에서 가리킬 대상과 표시된 답변 |
| validation | SUPPORTED / CONTRADICTED / INSUFFICIENT / UNCHECKED와 검사 방법·이유 코드 |

`SUPPORTED`는 정해진 검사에서 뒷받침됐다는 뜻이며 모델이 무오류를 인증했다는 뜻이 아니다. 상태 카드와 직접 인용에는 rule/extractive 검사 방법을, 생성 해석에는 semantic 검사 방법을 기록한다.

수동 확인사항은 requirement_key가 없어도 fact_id/source_ids로 인용한다. 여러 사실을 한 문장으로 요약하면 각 하위 주장에 필요한 source가 남아야 한다. 참조가 없는 사실을 일반 안내문으로 위장해 내보내지 않는다. 제외된 주장을 후속 대상 목록이나 대화 요약에 사실로 남기지 않는다.

### 2.3 D-01 집계의 결정

- `answerable_count`: askable=true인 항목만 센다.
- `unanswerable_count`: questions 중 askable=false인 항목 수. 별도 원문/입력 불가 이유 확인 대상으로 표시한다.
- `manual_review_count`: 자동 판정 밖 원문 확인 항목. 위 질문 개수와 구분한다.
- 같은 사실의 여러 분류가 겹치면 ID로 추적한다. 상호 배타적이지 않은 세 숫자를 무조건 합쳐 총계로 보여주지 않는다.
- “현재 시스템이 추가 답변을 받을 항목은 0건”과 “회사정보가 완전하다/더 확인할 것이 없다”를 동일시하지 않는다.

### 2.4 검증·복구 예산 — 초기 구현 기본값

아래는 이번 설계 기본값이며 벤치마크 결과나 특정 모델의 성능 보장이 아니다. 설정과 trace에 남긴다.

| 항목 | 기본 상한 |
|---|---|
| 최초 답변 생성 | 1회 |
| 최초 의미 검증 | 사실 주장 전체를 묶어 1회. 주장이 없는 안내나 서버 직접 출력은 생략 가능 |
| 실패 주장 수정 | 최대 1회. 전체 대화를 다시 생성하지 않음 |
| 수정 주장 재검증 | 최대 1회. 재검증 전에는 해당 산문을 공개하지 않음 |
| 답변 생성·검증 계층 합계 | 정상 2회, 최악 4회. 최초 생성 이후 추가 호출 최대 3회 |
| 계층별 입력/출력 토큰 | 각 호출 입력 최대 16,000, 출력 최대 3,000. 전체 프롬프트·근거·직렬화 오버헤드 포함 |
| 서버 턴 처리 예산 | 초기 45초 deadline. 계획·읽기·검색·생성·검증이 남은 시간을 공유 |

네 번은 항상 호출하라는 뜻이 아니다. 동일 근거에 대한 무한 재질문·재검증은 하지 않는다. 원문이 부족한 문제를 재작성으로 해결하려 하지 말고 계획에 정의된 보완 검색 또는 부족 범위 표시로 처리한다. Q-001의 4회는 답변 품질 계층만의 상한이며 planner·query embedding·검색 보완 호출을 숨겨 전체 비용으로 보고하지 않는다.

복구 호출은 수정과 재검증 모두에 필요한 잔여 예산이 있을 때만 시작한다. 시간이 부족하면 즉시 부분 반환한다. SDK의 자동 retry도 실제 호출 시도로 집계하고 상한을 넘지 않도록 구성한다. 늦게 도착한 결과가 이미 반환한 답이나 새 턴을 덮어쓰지 못한다.

16,000토큰에 근거가 안 들어가면 필수 예외를 조용히 자르지 않는다. 필요한 단락을 선택·보완하거나 이번 답변이 다루지 못한 범위를 알린다. 긴 전체 요약을 무조건 3개 항목으로 제한하지 않는다. 입력·출력·호출 수 상한은 비용 통제 장치이지 과업을 완수하지 않아도 된다는 면책이 아니다.

모델 가격·요금제를 이번 결정에서 가정하지 않는다. Codex는 실제 사용할 모델 ID와 최신 단가로 예상 비용을 산출하고 input/output/reasoning usage와 실제 경과 시간을 기록한다. 모델이 반환하지 않는 사용량은 unknown으로 남긴다. 단위 비용 정보가 없으면 달러 금액을 만들어내지 않는다. 대량 평가·전체 인덱스 임베딩은 별도의 명시적 실행 예산을 확인한다.

45초는 장애 시 무한 대기를 막는 상한이지 목표 지연시간이 아니다. 기존 p50 8초/p95 20초는 여전히 측정 전 목표로 따로 추적한다. 실제 지연과 답변 품질을 보고 조정하되 검증을 몰래 끄지 않는다.

### 2.5 의미 검증과 부분 반환의 구체 기준

1. 모든 응답에 권한·scope·참조 존재·서버 상태 불변·실행 상태를 기계적으로 검사한다.
2. 생성된 공고/회사 사실은 원문·구조화 값과 비교한다. 숫자만 등장하는지 보는 검사는 의미 검증이 아니다. 주어·기준일·단위·비교 연산·AND/OR·부정·예외가 보존되는지 확인한다.
3. “참가 가능합니다”와 “현재 판정은 불가지만 A 조건만 충족하면 해당 항목은 달라질 수 있다”를 구분한다. `가능` 문자열 포함 여부만으로 판정하지 않는다.
4. 모델 검증은 동일한 제한된 EvidenceBundle에서 수행한다. 사용자 문서의 지시문은 검증 정책으로 실행하지 않는다. 동일 모델을 사용할 수 있으나 독립적 보증이라 주장하지 않고 사람 검수·공격 테스트로 보완한다.
5. CONTRADICTED는 수정 또는 제거한다. INSUFFICIENT/UNCHECKED인 특정 사실을 “아마”로 완화해 정답처럼 노출하지 않는다. 근거가 있는 사실과 직접 인용, 확인이 필요한 질문을 대신 제공한다.
6. 이미 통과한 나머지 주장과 서버 출력은 유지한다. 제외된 내용에 기대어 만든 결론·다음 행동도 함께 재점검한다.
7. 필수 요청을 빠뜨렸다면 “일부만 답변”으로 알리고 평가상 PARTIAL/FAIL로 센다. 안전한 부분 반환 자체가 과업 PASS를 보장하지 않는다.
8. 새 경로의 사실 산문은 검증 후 공개한다. 검증 전 토큰을 화면에 먼저 흘려보내지 않는다. 진행 상태나 서버가 만든 상태 카드는 먼저 표시할 수 있다.

검증기 장애로 확실한 정보도 모두 사라지는 제품을 만들지 않는다. 예: 상태 카드는 정상 표시하고, 서버가 가진 미달 요건명과 연결 원문을 보여주며 “자동 설명 일부를 확인하지 못해 원문을 함께 표시합니다” 정도로 한계를 알린다. 이 대체 경로도 별도 테스트한다.

## 3. Q-002 결정 — 채팅의 읽기와 인덱스 재구축을 분리

**결정: B 채택. 새 Copilot 채팅 경로는 인덱스를 준비됐는지 검사하고 읽는다. MISSING/STALE/CORRUPT일 때 숨은 임베딩·재구축·파일 덮어쓰기를 시작하지 않는다.** 인덱스 문제를 이유로 읽을 수 있는 최신 문서까지 막지는 않는다.

### 3.1 두 축의 준비도

- source 상태: AVAILABLE / PARTIAL / UNAVAILABLE / UNVERIFIED.
- index 상태: READY / MISSING / STALE / CORRUPT / UNVERIFIED / BUILDING / ERROR.
- READY는 해당 fingerprint에 맞는 검색 도구가 준비됐다는 뜻이다. 공고 원문 추출이 완전하고 조건 해석이 정확하다는 뜻이 아니다. source=PARTIAL, index=READY도 가능하며 전체 요약의 누락 위험은 별도 표시한다.

| 상황 | 채팅 동작 |
|---|---|
| 검증된 source + READY index | 기존 Hybrid/Point 검색 또는 범위형 전략 실행 |
| 검증된 source + MISSING/STALE/CORRUPT/UNVERIFIED index | 현재 버전의 검증된 추출 블록·섹션 직접 읽기로 전환. 새 임베딩·인덱스 쓰기 없음 |
| source 일부만 확보 | 확보한 문서 범위에서 답하고 누락 문서·조건 범위를 명시 |
| source 접근 불가/검증 불가 | 문서 사실은 유보. 별도로 검증된 저장 판정·UI 이동 안내는 제공 가능 |
| BUILDING | 이미 사용 가능한 동일 fingerprint 세대가 있으면 그것을 고정해 읽음. 없으면 직접 읽기/부분 반환. 무한 대기 안 함 |

**직접 읽기는 오래된 index.records를 다시 보여주는 우회가 아니다.** 권한·버전·현재 문서 집합·추출 출처를 확인한 블록을 사용한다. 직접 읽기에서도 사실은 인용하고 범위 부족을 추적한다. 원본 bytes를 매 질문마다 전부 재다운로드해야 한다는 뜻은 아니지만, metadata만 확인했는지 원본 hash까지 확인했는지는 구분해 기록한다.

채팅에서는 이미 준비된 index의 query embedding이 필요할 수 있다. 이를 문서 임베딩/재구축과 구분해 예산·외부처리 trace에 기록한다.

### 3.2 fingerprint 계약

정렬·직렬화 규칙을 고정한 다음 아래 변경을 식별할 수 있도록 한다.

- 공고/버전, 문서 ID와 문서 집합, 추가·삭제·추출 상태.
- 원본 SHA256, 추출 텍스트 또는 블록 SHA256, 추출 방식/버전.
- 청킹 버전·주요 파라미터, 임베딩 provider/model/dimensions, 정규화·index 형식 버전.
- 인덱스 세대 ID와 artifact hash. 작성시각만으로 동일성을 판정하지 않음.

hash가 없는 legacy manifest는 동일한 null 두 개로 일치 처리하지 않는다. 다시 입증할 수 없다면 UNVERIFIED다. 같은 version_id여도 추출 결과나 문서 목록이 달라지면 다른 입력으로 취급한다. 준비도 확인과 실제 읽기가 서로 다른 세대를 보지 않도록 요청별 snapshot/generation을 고정한다.

현재 20개 manifest는 조사 대상이지 자동 삭제·무효화 대상이 아니다. 실제 대조 결과로 각 상태를 판정한다.

### 3.3 책임 경계와 현실적인 구현

- **기술적 책임:** 기존 `apps/api/app/document_rag/`에 fingerprint/readiness/load 및 명시적 build 경계를 둔다. Copilot은 그 계약을 소비한다. Copilot 폴더에 인덱스 서비스를 복제하지 않는다.
- **운영 연결:** 배포·수집 후 재구축 시점·실행 권한은 Backend/LLM-RAG 경계에서 관리한다. 이 문서가 팀원에게 작업을 전달했다거나 운영 합의를 이미 받았다는 뜻은 아니다.
- **Codex가 지금 할 일:** 기존 모듈과 호환되는 readiness 및 읽기 어댑터, 명시적 재구축 진입점과 테스트를 같은 작업 브랜치에 구현한다. 공용 API 의미를 깨뜨리거나 DB 스키마·운영 수집기를 바꿔야 하는 경우에만 별도 설계 질의한다.
- **초기 운영 방식:** 명시적 사전 인덱싱 명령으로 선택한 공고 버전 하나를 준비할 수 있게 한다. 대규모 queue/worker 구축을 W1의 선행 조건으로 만들지 않는다. queue가 없는데 “백그라운드 재구축 예약 완료”라고 표시하지 않는다.
- 기존 `load_or_build_version_index` 호환 호출을 당장 모두 삭제할 필요는 없다. 단, v3.1 채팅에서는 읽기 전용 경계를 사용하고 그 호출이 build로 이어지지 않는지 spy/네트워크 차단 테스트로 확인한다.

### 3.4 명시적 재구축의 최소 계약

사전 확인(dry-run)에서 source 상태·선택 버전·문서/청크 수·대상 fingerprint·예상 임베딩 토큰·출력 위치를 보여준다. 실제 외부 임베딩 실행은 버전과 실행 예산을 명시한 운영 명령에서만 진행한다. 합성 fixture와 fake embedding 테스트는 즉시 구현 가능하며, 공용 데이터를 대상으로 라이브 명령을 자동 실행하지 않는다.

새 index는 임시 세대에 생성·검증하고 검증된 artifact 묶음만 게시한다. 읽는 도중의 기존 파일을 직접 수정하지 않는다. manifest와 index 파일 각각의 교체를 묶음 전체의 원자적 교체라고 가정하지 말고, 완성된 불변 세대와 작은 active pointer 등으로 독자가 한 세대만 읽도록 설계한다. 같은 version/fingerprint의 중복 build는 잠금·중복 억제로 제어하고, 실제 지원 프로세스 범위와 재시작 동작을 테스트한다.

실패하면 기존 세대를 손상시키지 않는다. 그러나 기존 세대가 현재 입력에 대해 STALE이라면 보존되어 있다는 이유로 현재 검색에 사용하지 않는다. 별도 감사/이전 버전 조회에만 명시적으로 사용한다.

## 4. 구현 전 환경 정리 — 막힌 검사와 가능한 구현을 분리

### 4.1 코드 기준 정렬

감사 시 로컬은 `49d4d1a`, 원격은 `ea613b2`였다. 감사 PASS는 로컬 SHA 기준이며 `_sync_visible_targets()` 실행 증거는 아니다. 이 문서 commit 이후 원격은 또 이동하므로 고정된 예전 SHA로 reset하지 않는다.

Codex는 현재 상태와 새 diff를 확인하고 감사 원본·audit-evidence를 보존한다. 대상 브랜치가 맞고 fast-forward가 가능한 경우 최신 동일 브랜치를 fast-forward-only로 반영한 뒤 새 SHA를 고정하고 검사한다. 파일 충돌/로컬 divergent commit이 있으면 덮어쓰지 않고 상황과 해결안을 보고한다. 개발용 기준 브랜치의 별도 변경을 병합하는 일과 같은 브랜치의 fast-forward 수신은 구분한다.

원격에 이 문서만 추가하며, `01-current-state-audit.md`와 `audit-evidence/`를 이 대화에서 따로 올리지 않는다. Codex가 원래 로그·runner와 함께 민감정보를 점검하고 묶어 보존한다. 존재하지 않는 원격 로그 링크를 만들지 않는다.

### 4.2 Python/Node 환경

감사에서 기존 venv의 실행기 문제가 보고됐다. 번들 Python과 다른 venv의 site-packages를 결합한 7개 검사 성공은 그 조건의 참고 결과이며 표준 실행 환경의 검증을 대체하지 않는다.

기존 venv를 삭제하지 말고 유효한 Python 3.12로 별도 검증용 venv를 만들어 저장소 의존성을 설치하고 `pip check` 및 필요한 import/검사를 실행하는 방향을 권장한다. 저장소 버전이 현재 패키지 소스에서 설치되지 않으면 임의 downgrade/새 lockfile 덮어쓰기 대신 재현 정보와 대안을 보고한다.

프론트는 저장소/CI가 요구하는 Node/pnpm 기준을 확인해 정렬한다. 감사 환경의 pnpm 11.19.0과 CI 10.15.0이 다르다는 이유만으로 오류를 단정하지 않지만, 검증 전 lockfile을 다른 major로 재작성하지 않는다.

### 4.3 DB/모델 조건

격리 DB가 없더라도 W0/W1 계약, D-01~03 회귀, 상태·target·준비도 합성 검사, 모의 도구 복합 대화 구현은 진행할 수 있다. DB와 모델 검증만 BLOCKED로 두고 전체 구현을 중단하지 않는다.

실제 DB 통합은 별도 PostgreSQL 16 대상의 host/port/database/사용자와 서버 identity를 확인한 뒤 진행한다. Docker 접근 실패와 Docker 미설치를 같은 의미로 보고하지 않는다. 격리 수단이 없으면 필요한 실행 조건을 사용자에게 알린다. 이 설계 문서 자체가 공용 Supabase 접속·seed·migration·초기화를 허용하지 않는다.

## 5. Q-001/Q-002를 고정할 회귀 검사

아래는 구현할 기대조건이며 이번 대화에서 실행한 결과가 아니다.

### 답변·인용·집계

- askable=false만 있는 경우 answerable_count=0, 입력 액션 없음. 혼합된 경우 정확한 분리와 중복 집계 방지.
- requirement_key 없는 수동 fact도 원문 source에 연결. 존재하지 않는 fact/source는 거부. 요건이 아니라도 원문 보기 가능.
- enum은 정상이고 결론·본문·caveat·next action 각각에 반대 판정을 주입해도 사실 답변으로 노출하지 않음.
- 단순 부정 단어 감지가 아니라 실제 반전과 올바른 부정문/가정/과거 버전 비교를 구분.
- 의미 검증 장애·시간 초과·불확실 결과에서 서버 상태와 유효 인용/통과 주장은 유지, 미검증 주장은 노출하지 않음.
- 한 번의 수정과 재검증 후에도 실패하면 추가 호출을 하지 않고 부분 반환. SDK retry 포함 상한·늦은 응답 차단 검사.
- 올바른 답변 fixture도 충분히 넣어 과잉 거절을 확인. 전부 거절해서 오류율 0을 만드는 구현은 실패.
- 수치·기간·예외가 바뀐 예시와 동일 의미의 말바꾸기 예시 모두 검사. 특히 J05 기관 제외와 식수·기간 조건을 보존.
- 필수 항목을 제외한 부분 반환은 안전성 PASS와 별개로 과업 PARTIAL/FAIL. 주장 정확도와 응답 범위·재질문 비율을 함께 보고.

### 원문·인덱스·재구축

- 같은 version에서 원본/추출 hash 변경, 문서 추가/삭제, model/dimensions 변경을 각각 탐지.
- hash 없는 manifest를 READY로 오인하지 않음. 일부 문서 미추출 상태와 index READY를 분리.
- STALE/MISSING/CORRUPT에서 채팅이 build·document embedding·index save를 호출하지 않음.
- 검증된 현재 블록이 있으면 직접 읽기로 인용된 답을 제공. stale index.records를 현재 원문 대신 사용하지 않음.
- 원문 불가 시 오래된 조건을 생성하지 않고 확인된 상태·한계만 제공.
- 요청 중 generation 교체와 동시 build에서도 manifest/index가 섞이지 않음. 실패·중단 시 기존 세대 보존.
- READY Point QA의 기존 동작 유지. 전체 요약은 관련 청크 존재만으로 PASS하지 않고 검수된 예외·필수 조건 coverage를 평가.
